## 4. The combined persistence contract

Each property was traced in the code and tied to the test that pins it. The first three groups come from 1D's design and were re-read in the merged tree by seven independent read-only reviews of the code (lenses: candidate lifecycle; atomicity and concurrency; migration and schema; audit contract; service obligations; secret handling; mutation evidence), each followed by a skeptic pass on every medium-or-higher defect. A review that ran no tests proves only that the code reads that way; the runs are in section 7.

**Candidate lifecycle.** One live candidate per user: the filtered unique index `UX_UserTotpReplacementCandidates_Live` on `UserId` where `Status < 2`, with staging serialised on the active credential row (`UPDLOCK, HOLDLOCK`), so the index is the last arbiter. Ownership: `UserId` is named in every read, verification and switch statement (X05 and X12 remove the two ownership conditions that the staged-against check masks and are caught). Expiry: the database's own clock only (`SYSUTCDATETIME()`), bounds 1 second to 24 hours enforced before any SQL. Supersession: the older live candidate is set to Superseded, its version bumped and its secret wiped in the same transaction as the insert. Consumption is terminal: only Staged verifies and only Verified switches, nothing moves a row back, and a re-stage purges consumed and superseded history under a new candidate id (so a consumed or superseded id degrades to `NotFound` afterwards: the service must treat Consumed, Superseded and NotFound as one "this candidate is dead" family). The version is compared in the same statement as the state, the id and the owner.

**Credential and code integrity.** The switch is one conditional `UPDATE` over the credential and the locked candidate (verified, version, unexpired, same user, staged against the credential that is active now); on exactly one row it also consumes the candidate and replaces the recovery codes in the caller's transaction, otherwise it diagnoses without writing. Every non-`Applied` outcome changes nothing (a theory over every refusal asserts the active credential and the codes byte for byte). `MarkEnrolledAsync` is one `ExecuteUpdate` conditional on pending and on the expected identity; `UpsertPendingAsync` and the switch assign new identities, completing enrollment does not. The matched TOTP step becomes the last used step in the same statement (X11). At rest: the candidate holds only the protected bytes the caller gives it, a consumed or superseded row holds zero bytes, and the switch moves the protected bytes without decrypting.

**Concurrency and lock order.** Credential row, candidate rows, recovery-code rows, in that order, in stage, verify, switch and the credential delete. Eight parked cases (both modes) cover stage, verify, switch, reset and regeneration; a reset overlapping a switch surfaces as `DbUpdateConcurrencyException` and nothing is partially updated (the reset deletes the tracked row with its row version). No path on these code paths catches `DbUpdateConcurrencyException` and reports success. Two defects found on this lens are recorded as findings F-1 and F-2 (section 9); they are fail-safe and are not fixed here.

> **Correction (2026-11-09).** F-2 was not fail-safe. The independent review demonstrated it as a replay of an accepted TOTP code and the success of a sign-in with a retired authenticator (B-1, blocking). F-1 was demonstrated as SQL error 1205 in both isolation modes, both for the same user and across users. Its rollback was clean (R-1). The eight parked cases ran on retrying contexts and could not observe a retried deadlock. See the remediation record.

**Interaction with the accepted coordinator and viability contract (new here).** The viability facts read `UserTotpCredentials.IsEnrolled` and the unused recovery codes (`SqlAdministratorFactsReader`); a candidate lives in its own table and never in the credential row, so a staged or verified candidate changes nothing the facts see. Real-SQL cases in both modes now run the *real* 1D operations in a *real* coordinator scope (section 8): a staged and a verified candidate leave the facts equal; the real switch inside the scope's transaction is decided `Allowed` with basis `PostureOnly` and evidence `NotRequired`, and commits atomically with the attempt (new identity, exactly the new codes, candidate consumed); the same attempt rolled back after the switch restores the identity, the secret, the step and every code and leaves the candidate verified at its version (it still switches afterwards); a reset (credential delete plus code removal plus candidate removal) judged as a replacement is refused with `recovery_access_posture_reduced` and its rollback restores the candidate. The lock the coordinator takes (the administrator-set gate) is taken before the credential lock by contract (`EnterAsync` is the first lock after the operation lock); no path in `src` takes the credential row and then the gate.

## 5. Migration and data compatibility

Verified by reading the migration, the model configuration and the snapshot together, and by running them.

* **Model and snapshot.** The migration, the entity configuration and the snapshot agree column by column (types, lengths, nullability, the index name and filter, the cascade foreign key). The existing consistency test (`AppertureDbContextModelConsistencyTests`, `HasPendingModelChanges`) passes on the integrated tree in the unit run.
* **Up.** `CredentialId` is added nullable, every existing row (pending and enrolled) gets its own `NEWID()`-derived lower-case 32 character value, then the column becomes `NOT NULL nvarchar(64)`. No secret, step, timestamp or enrolment state is changed (a seeded installation migrated by the supported migrator compares equal column by column). The candidate table starts empty.
* **Filtered unique index.** Predicate `[Status] < 2`; the database refuses a second live candidate (error 2601) and allows history.
* **Down.** Drops the candidate table and the column. What a rollback loses is exactly the candidates and the identities; it does not touch a credential, a recovery code or an enrolment flag. The existing migration test proves that for credentials alone; a round-trip test added here (`MfaReplacementCandidateRoundTripSqlServerTests`, passed together with the three existing migration cases: 4 of 4) proves it with live and historic candidates present and proves that a second upgrade issues new identities, so a candidate staged before the rollback can never match a credential afterwards.
* **Disposable catalogs only.** Migration tests create and drop their own catalogs (`Apperture_..._` prefix, the established fixture); no real development or production data was touched.
* **Residual observations (not defects of the merge).** The column is `NOT NULL` without a default, so an older host build still writing credentials would fail loudly on the first create (an unsupported topology: the deployment documents one host version per instance). **Correction (2026-11-09, R-3):** no such statement existed. `deploy/README.md` now states the constraint in "Authenticator records after upgrading": rolling back only the program is unsupported, and the schema must be downgraded or the pre-upgrade backup restored first. The migration suite pins the 515 refusal and the downgrade; the entity defaults `CredentialId` to the empty string, so a future writer that forgets it stores an empty identity instead of failing (a CHECK on the length would remove that, left to the owner). A pending credential is replaced in place by a new begin, whose identity changes, which is what makes a stale enrolment fail.

D-1 to D-3 stay open from the [decision record, section 15](iam10-2b-wp4b-decision-record.md); they are mandatory for the service package.

* **D-1.** Use the canonical user id of the row the service loaded, never caller-typed, cased or trimmed input, for the candidate calls, the recovery-code records (the switch requires them to be owned by that user, ordinally) and every `Verify...Async`; the guard compares ordinally.
* **D-2.** Assert the transition the reducer itself performs (a revocation must change the designation of the named user, and only that), and do not rely on the guard to notice a no-op or a different change.
* **D-3.** Call `Verify...Async` last, after every write, and never write after the decision; a kept refusal records `decision.Evidence` (the actual configuration evidence).
* **U1, ordering.** Outside any unit or gate: load the user row and take the canonical id; load the stored credential and the candidate; generate the secret and the recovery codes (plaintext and hashes) and call `coordinator.PrepareAsync()`. Stage the candidate in its own transaction, show the secret once, and let the operator type a code with nothing held. Verify the code against the **candidate** secret (unprotected with the candidate's own `ProtectorKeyId`), with replay protection against the **active** credential's `LastUsedStep` (`Rfc6238Totp.Verify(...)` skips steps not greater), then `MarkVerifiedAsync(user, candidateId, candidate.Version, matchedStep)` outside the unit. Persistence records the step; it does not prove possession. Inside the unit: `EnterAsync` as the first lock after the operation lock, a new scope per attempt, `CaptureBeforeAsync`, `SwitchAsync` (version from the verify result, codes hashed before the unit), then `VerifyReplacementAsync(canonicalId)` last; stage `auth.mfa.replaced` with `decision.Evidence`. Show the new plaintext codes only from the committed result. Do not call `ReplaceAllAsync` or `DeleteAllAsync` after the switch: both delete candidate rows.
* **U2, outcomes.** Every non-`Applied` outcome wrote nothing: end the unit with `DeclareNoOp` or a typed conflict. `NoActiveEnrollment`: say there is nothing to replace and never fall back silently to a destructive reset. `NotFound`, `Superseded`, `Consumed`, `Expired`: restage (treat the first three as one family; after the next stage a consumed or superseded id reads `NotFound`). `VersionMismatch`: reload and restage. `AlreadyVerified`: another caller holds the version; restage, never read the version with `GetAsync` and switch. `NotVerified` from a switch is a service defect (the verify step was skipped or lost). `ActiveEnrollmentChanged`: the account's authenticator changed since staging; restage and tell the operator. A refusal by `VerifyReplacementAsync` after an applied switch throws the typed refusal; the unit rolls back, the candidate stays verified at the same version and the old authenticator and codes stay. The wait for the gate counts against the candidate lifetime (the database clock decides), so choose a lifetime that covers verification plus the gate bound.
* **U3, typed conflict handling (no retry infrastructure here).** The candidate repository's own calls do not raise `DbUpdateConcurrencyException`; they return typed outcomes, may surface SQL deadlocks that the unit's execution strategy retries, and throw `InvalidOperationException` only for impossible states (defects). The tracked repositories do raise it: `_totp.DeleteAsync`, `_totp.UpdateLastUsedAsync`, `_recoveryCodes.ReplaceAllAsync` and `DeleteAllAsync`, so the reset and regeneration reducers of the same package can (a reset overlapping a switch). The service boundary should catch it once and translate it to a typed, retryable `GovernanceConflictException` ("the authenticator changed while this request ran, run it again"); the unit already owns bounded reruns, and a second automatic retry would hide the competing writer. The emergency CLI catches only `EmergencyAccessException` and a few audit exceptions today, so its mapping must add it. Treat SQL error 1205 on the paths of F-1 as retryable until F-1 is fixed.
* **U4, the I-R3-1 observation (assessment and specification).** The previous review noted that the replacement falls through to the full evaluation when an ungated change moves facts between `CaptureBeforeAsync` and `VerifyReplacementAsync` (a pending Entra link proof; an ungated designate or revoke until those writers take the gate). Reading the guard: `DecideReplacement` applies the posture-only predicate only when `OnlyAuthenticatorChanged` holds; otherwise `FullEvaluation` judges the net effect on the two invariants, which allows when an Entra-independent ordinary administrator remains and does not look at the Recovery Access posture. Conclusion: **conditionally yes, the intended replacement predicate can be bypassed by an intervening identity change, but a correct 1D switch cannot itself reduce the posture** (it leaves an enrolled authenticator and at least one unused code, so a posture loss would need the intervening writer's own change to cause it), so no harmful commit is reachable today; the reachable effects are a spurious `ConfigurationUnavailable` refusal and the loss of defence in depth. The narrowest check, as a specification of the service and not a change to the guard: for `ViabilityMutation.AuthenticatorReplacement`, accept a decision only if `decision.Basis == ViabilityDecisionBasis.PostureOnly`; a refusal that is itself `RecoveryPostureReduced` also has basis `PostureOnly` and is surfaced as it is; any other basis (`LocalSignIn`, `FullEvaluation`, `ConfigurationUnavailable`, `InputsUnchanged`) means facts moved, so roll back whatever the verdict and throw a typed retryable conflict ("administrator access changed while the replacement ran, run it again"); do not report a `ConfigurationUnavailable` that came from the fall-through as a configuration problem. A retry recaptures, and after a one-time link proof the facts are stable. It needs no guard change, no new read and no version token. Pin it at service level with a fake store that proves a pending Entra link between capture and verify, a posture-only happy path and an unavailable-configuration case (the guard test `AdministratorViabilityPostureDecisionTests` already pins that the fall-through returns a basis other than `PostureOnly`). The window after the verify read and before commit is not observed; only add-only ungated writers can act there while the gate is held, as for every reducer.
* **U5, other facts.** `MarkVerifiedAsync` stores whatever step it is given and the switch copies it to the last-used step without comparing it with the active one: pass the step that actually matched the candidate secret. Keep `(candidateId, version)` in the operator's process; persistence has no session binding. Call `DiscardAsync` when the operator abandons the replacement or the service sees `Expired`. A candidate also vanishes on reset, on code regeneration and on any `ReplaceAllAsync`/`DeleteAllAsync`, by design. The switch needs at least one recovery code and every code owned by the same canonical user.
* **U6, guards.** Extend `AdministratorViabilityWriterCoverageGuardTests` with patterns for `StageAsync`, `MarkVerifiedAsync`, `SwitchAsync` and `DiscardAsync`, and update the two pins in `MfaReplacementAuditContractTests` ("files naming the candidate repository", "no production caller yet") and the two catalog comments that say no service writes the actions yet, in the commit that adds the first caller.
* **U7, audit mapping.** One function maps a `ViabilityDecision` and its mutation to the refusal event (`operation`: `mfa.replace` for `AuthenticatorReplacement`, `mfa.reset` for `AuthenticatorReset`, `recovery_access.designate`, `recovery_access.revoke`; `code` from the typed refusal) with a defined value for null evidence, and a test over every mutation and every evidence value. The success event is `AuditEvents.MfaReplaced(userId, decision.Evidence)`.
* **Residual from the foundation (unchanged).** Ungated recovery-code consumption (C-14) races a switch that deletes all code rows; a sign-in can see a tracked-update concurrency failure during a switch (pre-existing in kind, regeneration does the same).
  - **Update (2026-11-09).** The TOTP sign-in no longer uses a tracked update. The step write is conditional (B-1 remediation), so a sign-in during a switch fails cleanly instead of raising a concurrency exception. U3's list of tracked writers no longer includes `_totp.UpdateLastUsedAsync`, and its note to treat 1205 on the F-1 paths as retryable is superseded: F-1 is fixed.

### Service-entry obligations from the independent review (added 2026-11-09)

The review of `072b7e94` added these obligations. They are mandatory for the service package, beside D-1 to D-3 and U1 to U7. None of them is implemented by the B-1 remediation, which needed none of them.

* **S-1, audited unit and lost acknowledgement.**
  - `SwitchAsync` also runs standalone, with no audit row and no gate. Call it only inside the audited unit; consider requiring an ambient transaction.
  - On a lost commit acknowledgement the rerun reports `Consumed` although the switch applied. Make the result idempotent: on `Consumed`, compare the stored `CredentialId` with the expected new state before reporting.
* **S-2, never commit after a failed switch.** There is no savepoint and `XACT_ABORT` is OFF, so a statement error part-way through the switch leaves earlier statements applied until the caller rolls back.
  - Never catch and continue after a `SwitchAsync` exception inside the unit.
  - Validate distinct recovery-code ids and lengths before the switch.
* **S-3, canonical identity and collation.** A mis-cased user id under the default case-insensitive collation, together with pre-consumed code records, could reduce the Recovery Access posture while the guard still returns `PostureOnly`. D-1 (the canonical id of the loaded row) covers it. A cheap persistence defence for the service package to consider: `SwitchAsync` compares the stored `UserId` ordinally and refuses code records with `ConsumedAtUtc` set.
* **S-4, refusal for a non-PostureOnly replacement decision.** U4 rolls back when `decision.Basis != PostureOnly`. Define its refusal code (retryable "administrator access changed while the replacement ran") and its audit rule: whether a refusal row is written after the rollback, and with which `operation`, `code` and evidence.
* **S-5, evidence classification.** `MfaReplaced` evidence is optional in the schema, and the refusal event requires it. Define the value recorded for null evidence in both the success and the refusal events (U7), and test it over every mutation and evidence value.
* **Recovery-code acceptance under concurrency (to assess, not a demonstrated finding).** `ConsumeRecoveryCodeAsync` lists the unused codes and then marks the matched one consumed with an unconditional tracked write. Two concurrent sign-ins with the same recovery code may therefore both succeed; the review established this by reading the code, not by a run. Assess it, with a real-SQL interleaving, in the remaining native-MFA sign-in hardening. The likely fix mirrors B-1: a conditional `ConsumedAtUtc IS NULL` write whose result decides the sign-in. It was deliberately not changed here.
