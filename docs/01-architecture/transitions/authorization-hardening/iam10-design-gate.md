## 0. Summary

**The shape of the proposal.**

1. **One definition of "holds".** An immutable `EffectivePermissionSet` is computed from role assignments and answers `Allows(permission, target)` with exactly the evaluator's rule. The evaluator, the two subset rules, the effective-access endpoint and the capability flags all use it. A grantor "holds" a permission if and only if the evaluator would allow it (P-1). This avoids a second algebra.
2. **Two subset rules, evaluated inside the audited unit under a role-row lock** (P-2, P-3, P-5). Rule 1: a permission added to a role must be held by the actor. Rule 2: a role may be assigned only if every permission in it is held, and the Platform Administrator role only by a Platform Administrator. A recommended symmetric rule covers removal (P-4, OQ-2).
3. **The `role.manage` implication is deleted** and replaced by an explicit, preserving, idempotent data step that is visible in the role editor and in one audit summary (P-6, P-32). The Platform Administrator keeps a narrow, named system-role floor.
4. **The last-administrator guards get one gate and one viability query** (P-8 to P-11). Serializing the existing guards is not enough: two local-only administrators can have both credentials disabled **one after the other**, with no race, because the guards only act when the assignment count is exactly one (G-9). The AUD-1.2 acceptance for F-10A needs a viability-aware predicate (C-1, OQ-3).
5. **`PermissionDefinition`** adds name, description, category, sensitivity, step-up and origin around the **unchanged** identity triple (P-12 to P-16). Module declarations gain the same fields. The dead `IsPrivileged` and `ActionCategory` scaffolding is deleted.
6. **Scope composition is two axes, not a new scope key** (P-21 to P-27). Module and environment stay in the prefix hierarchy. Context is a second, independent dimension carried on the **assignment** and on the **target**, never a string in `ScopeKeyConstants`. That keeps D-11 literally true and the pinned test green. `integration:{id}` is an identity (a principal kind and a record owner), never a containment prefix. One `IAuthorizedContextResolver` contract returns a typed predicate to apply **before** paging. RC1 implements none of it.
7. **The evaluator gets a result type and declarative step-up at the seam** (P-28, P-29): a flagged permission is denied by the existing `bool` path without per-site adoption, so a flag cannot be silently unenforced. Denials of Elevated and Critical permissions are audited only by the enforcing helper, never by capability probes (P-30).
8. **Recovery Access is carried forward unchanged** (P-35). A code trace shows the grant-all branch belongs only to the legacy break-glass login, not to Recovery Access (G-14). The same trace shows the audit `viaRecoveryAccess` flag hangs off that legacy marker. That is a finding for the owner, not a change to AUD-1.2 or IAM-9 (OQ-7).

## 1. Scope and non-goals

**In scope.** The escalation paths and the subset, implication and migration rules (A). The administrator-viability races (A). `PermissionDefinition`, sensitivity and step-up metadata, and module registration (B). The catalog questions carried in from IAM-9 and SEC-2 (B). The six scope-composition questions of the program gate §6.3 (C). The result type, declarative step-up, refusal auditing, migration behaviour and the tests that prove them (D).

**Not in scope.**
- Any context-scoped implementation, scope constant, role, grant, capability or UI (D-10, D-11).
- A permission-set implementation, deny rules, service accounts, agents, or a second policy engine (audit plan IAM-10 non-goals; program gate §4.4).
- IAM-11 content: credential recovery flows, decommission, session revalidation, Entra unlink, throttling. This gate only defines the shapes IAM-11 consumes.
- Reopening SEC-2 or IAM-9. Recovery Access behaviour is carried forward as accepted.
- A general security audit. Findings in §2 are limited to those that bear on this design.

## 3. Recommended decisions

### 3.1 A. Escalation: the held-set and the two subset rules

| # | Decision | Alternatives considered | Why |
|---|---|---|---|
| **P-1** | **One definition of "holds".** Introduce `EffectivePermissionSet`, built from a user's role assignments (stored grants plus the system-role floor of P-6). `Allows(permission, target)` implements the evaluator's current rule exactly (action, resource type, containment). The evaluator, the subset rules, `effective-permissions` and the capability flags all call it. A grantor holds `G` if and only if `Allows(G, G.Resource.ScopeKey)` is true for their set. A grant with no resource keeps today's broad matching (compatibility) and is reported by the data step (P-32), not silently changed | A separate subset algebra comparing grants pairwise. A second algebra can disagree with the evaluator, which is how escalation paths are born | Satisfies D-09 (no second policy engine). Makes "holds" testable against the evaluator by construction |
| **P-2** | **Rule 1: grant subset.** Creating a role with grants, or replacing a role's permission set, requires the actor to hold every permission **added** by the change. Removing a permission needs no further holding. System roles stay immutable (IAM-8). Module-scoped permissions follow P-1: an instance-level grant of the same action and type covers any module; a grant at `module:X` covers `module:X` and its slots only. The check runs **inside the audited unit, after the role row is locked**, with the actor's set computed fresh (P-5) | Check before the unit only (the current shape). Exposed to the actor losing authority, or the role changing, between check and commit | Closes scenario 2 ("unbounded grant"). Module-scoped delegation falls out: a holder of `permission.assign` plus only `module:X` permissions can grant only those |
| **P-3** | **Rule 2: assignment subset.** Assigning role `R` to user `U` requires (a) the actor holds every permission in `R` as read under the role lock, and (b) if `R` is the Platform Administrator role, the actor is a Platform Administrator. The target user may be the actor: no separate self-assignment rule is needed, because (a) and (b) do not depend on the assignee, so self-assignment can add nothing the actor does not already hold. The existing system-managed (Recovery Access) refusal is unchanged | A rule that only forbids self-assignment (leaves "assign admin to a colleague who assigns it back"). The audit plan's "role permissions are a subset of the grantor's" is adopted as (a); (b) is stated separately because the Platform Administrator role has special repair-maintained grants | Closes scenario 1 ("self-promotion") and the colleague variant |
| **P-4** | **Symmetric removal (OQ-2).** Removing `R` from `U` requires the same (a) and (b) as assigning it, except that a user may always remove a role from themselves. Last-administrator guards still apply | Removal needs only `role.assign` (today). Then any `role.assign` holder can strip other administrators of everything except the last one | Denial of administration is also an escalation of the remover's relative power. Cheap to state, cheap to test |
| **P-5** | **Race closure.** The assign, create-with-grants and replace paths read the role row `UPDLOCK, HOLDLOCK` (the pattern `TryDeleteUnassignedAsync` already uses) before comparing, so a concurrent edit or assignment of the same role is serialized. The actor's authority is recomputed after the lock through a re-authorization callback (the SEC-2.1 pattern). The assignment insert replaces check-then-insert with a locked insert, with the primary key as backstop | Application lock for all role operations. Wider than needed | Closes "assign R while another administrator adds a permission to R" and "actor's role removed mid-request" |
| **P-6** | **Delete `ImpliedByInstanceRoleManage`.** Keep a **named system-role floor**: the set the evaluator grants to holders of `role-platform-administrator` regardless of stored JSON, restricted to the current governance and authentication-configuration surface minus the `user.read` on Role stopgap (P-18). The floor is part of `EffectivePermissionSet` (so it counts as held), and a test asserts floor ⊆ repair arrays ⊆ the administrator's explicit grants after startup. It exists so a malformed `PermissionsJson` cannot lock out administration (the IAM-10.2 invariant). `workflow.execute` on WorkflowInstance at instance scope is a named, administrator-only floor member, documented as intentionally absent from the catalog (G-4) | Remove the floor and rely on startup repair. Leaves a window at startup and on a malformed row | Preserves "the Platform Administrator is never locked out" (audit plan IAM-10.2) without a second implication path |
| **P-7** | **Every ordinary writer of grants or assignments is under the rules; every exempt writer is named.** A code survey† finds these production writers. **Ordinary (rules apply, actor is the current principal):** `UserManagementService` (`ReplacePermissionsAsync` at `:168`, `AssignToUserAsync` at `:801`, role create) and `UserProvisioningService.TryAssignRoleAsync` (`:420`: the initial role given when an administrator provisions or approves a user, which today needs only `role.assign`). The provisioning path applies Rule 2 with the approver as the actor. **Exempt (system actors, not a person's authority):** `BootstrapPlatformAdminAssignment`, `DevTestUserBootstrapHostedService`, `RealBootstrapRecoveryService`, `FirstAdminBootstrapService`, `EmergencyAccessService` and `PlatformAdminRoleRepairService`. A guard test lists the writers and fails on a new one that is in neither group | Apply the rules inside the repository (catches every writer, but the repository cannot know the actor and must stay a store). Leave provisioning on `role.assign` only (a second route to scenario 1) | Closes the route where a `user.manage` plus `role.assign` holder gives a new account a role they could not assign directly |

### 3.2 A. Administrator viability (F-10A, F-10B)

| # | Decision | Alternatives | Why |
|---|---|---|---|
| **P-8** | **One gate.** `IPlatformAdministratorSetGate`, modelled on the ownership mutation gate: one resource name, an exclusive transaction-owned application lock, a bounded wait, a typed busy exception. It is acquired as the **first lock after the operation lock** by every path that can reduce the number of viable administrators: role removal, identity-link removal, local credential disable, the Entra-primary policy, and (when they ship) IAM-11 disable, decommission and Entra unlink. Plain role assignment does not take it | Row locks on the administrator assignments (the role delete pattern). They do not cover credential and link changes, which do not touch the assignment rows | One lock name means one order and no deadlock between these paths. The ownership gate already proves the pattern |
| **P-9** | **One viability query.** `IPlatformAdministratorViability` returns the set of viable administrators in a single definition: holds the Platform Administrator role; is not system-managed (Recovery Access is excluded, OQ-3); (when IAM-11 adds status) is active; and has a viable sign-in method, meaning an enabled local credential **or** a proven Entra link while Entra is usable. A second flavour requires an enabled local credential (the "Entra-independent" count of F-10B). All guards and the policy call it **under the gate**. The refusal predicate becomes "the change would leave no viable administrator", replacing the `adminCount == 1` special cases. Refusal codes, audit actions and rows are unchanged. The "already in that state" check runs **before** the guard, so a no-op request is a silent no-op, not a recorded refusal (the AUD-1.2 low finding) | Keep `adminCount == 1` and only add the lock. Fixes the race and leaves G-9(b) | Closes G-9(a) and (b) and the disagreement between the guards and the policy. Conflict C-1 explains the one behaviour change |
| **P-10** | A wait that exceeds the bound throws a typed busy exception, mapped to a retryable status with a stable code, as the ownership gate does. The read-only display (`DescribeAsync`) uses the query without the gate | Block indefinitely | Operator mutations are rare; a bounded wait is enough |
| **P-11** | The refusals get typed exceptions and explicit statuses: 409 with stable codes for `last_platform_administrator`, `last_viable_sign_in_method` and `last_local_credential`, replacing the 404 and the unhandled link exception (G-10). Clients (the user pages) are updated in 10.4 | Keep the status codes | A server refusal that reads as "not found" or a 500 hides a safety control |

### 3.3 B. Permission definitions and sensitivity

| # | Decision |
|---|---|
| **P-12** | **`PermissionDefinition`** (in `Core.Domain.Governance`). Fields: `Identity` (the unchanged `PermissionDescriptor`: action, resource type, scope key), `DisplayName` (required, ≤ 80 characters), `Description` (required, one sentence of what the holder can do, ≤ 300), `Category` (a small closed enum: Identity and access, Configuration, Integrations and connections, Operations, Data and notifications, Audit and monitoring, Platform, Modules; the exact set is settled in 10.1), `Sensitivity` (`Standard`, `Elevated`, `Critical`), `RequiresStepUp`, `GrantedToPlatformAdministratorByDefault`, `Origin` (`Platform` or `Module`), `ModuleId?`, and the existing `Family`. The canonical permission key stays the audit `Identity()` form (`action@resourceType:scopeKey`). **Any later field is additive with a default** (for example a context-scoping flag or permission-set membership); nothing in this record may need a breaking change to add one |
| **P-13** | **Registry.** `RegisterPermission(PermissionDefinition)` replaces the descriptor-only overload in production code. A definition with no display name or description fails registration. A second registration of the same identity with different metadata conflicts, as it does today. `GetPermissionDefinitions()` serves the catalog endpoint. The `Source` and `ModuleId` shown to clients come from `Origin` and `ModuleId`, not from parsing the scope key |
| **P-14** | **Module declarations.** `ModulePermissionDeclaration` and `ModuleGovernedActionDeclaration` (which also registers a permission) take `DisplayName`, `Description` (both required), `Sensitivity` (default `Standard`) and `RequiresStepUp` (default false). A declaration that omits the required fields fails registration with the module id in the message, as other invalid declarations do. The SDK is labelled preview, so no compatibility shim is kept; the five in-tree modules are updated. A module cannot decline the platform administrator default (the repair merges every module-scoped permission). `IsPrivileged`, `GovernedActionDescriptor` and `ActionCategory` are deleted. Modules are trusted in-process (ADR-0001): sensitivity is a declared classification for operators, not a security boundary against the module |
| **P-15** | **Classification rule and proposed values** (the owner confirms the table in 10.1 review). **Critical:** can change who holds authority, replace credentials or identity trust, read or write secrets, or introduce executable code. **Elevated:** changes configuration or runtime and alerting behaviour, deletes data, makes an outbound call with a stored credential, or reads audit. **Standard:** reads of operational data and routine authoring. ### 3.5 C. Scope composition (RC1 §6.3, questions 1 to 6)

All six are design rulings. Nothing here is built in RC1 (D-10), no scope constant is added (D-11), and nothing is "reserved" in code. The only RC1 consequences are the do-not-freeze constraints of P-27.

| # | Question | Recommendation | Alternatives considered |
|---|---|---|---|
| **P-21** | **1. Scope algebra** | **Two independent axes, evaluated together by the existing containment function.** Axis 1 is the current scope key (`instance`, `environment:…`, `module:…`, slots), untouched. Axis 2 is **context**, which is **not a scope-key string**. A grant carries, through its assignment (P-23), either "any context" or one context. A target carries its owning context (P-22). A check passes only if axis 1 contains (today's rule) **and** axis 2 matches. Instance grants stay universal on both axes. A context-constrained grant **never satisfies a check whose target carries no context** (fail closed), so a confined principal is refused every endpoint that has not been adopted, which is the safe default and lets adoption go one endpoint at a time | **A composite key** (`context:C/module:M` or the reverse). A prefix-only evaluator supports one hierarchy: either order makes one of "grant at module M covers module M in context C" and "grant at context C covers all modules in it" fail (addendum B.6). **Make context a prefix level of the one key.** Same problem, and it fails every module-targeted check (ten services target `module:{id}`). Two axes also keep `NoContextScopeKeyFormExists` true as written |
| **P-22** | **2. Target-scope derivation** | `IGovernedResourceIdentity` gains an optional **`ResourceContextId`**, kept separate from `OwnerId` (which ADR-0012 reserves for principal ownership and the code never reads). Integration, Connection and Schedule fill it from their direct context column (Schedules have no governed identity today and gain one); a Binding derives it from its Integration and Connection, since it has no column of its own (CTX gate R4). **Live checks use the current owner, read in the same unit as the action and re-authorized under lock** (the ownership-move race SEC-2.1 already handles). **History reads** (runs, schedule runs, audit) use the snapshot stored on the row where one exists, and the live owner otherwise (OQ-8). `ResourceContextId` is distinct from `ScopeKey`; `Integration.ScopeKey` and `Connection.ScopeKey` stay authorization text and gain grammar validation at write time (G-16) when this is built. **Deliberately superseded when built (not now):** the sibling assertion in `ResourceContextAuthorizationNonChangeTests` that governed identities ignore ownership, CTX-3 gate §9.3 ("no context-scoped role assignments, roles, grants or capabilities"), IAM-8 R6 and the matching sentence of ADR-0044. `NoContextScopeKeyFormExists` stays green | Derive context from the Integration for every check (breaks standalone schedules and history, CTX gate R5). Authorize history by current owner (a moved integration's old runs would follow it and disappear from the previous owner's confined principals) |
| **P-23** | **3. Assignment shape** | **Scope on the assignment, not the grant.** `RoleAssignment(PrincipalKind, PrincipalId, RoleId, ContextConstraint)`, where the constraint is "any" or one context. Roles stay reusable ("Operator" assigned at Application A and at Application B). The `UserRoles` key `(UserId, RoleId)` becomes `(UserId, RoleId, ContextKey)` with a sentinel for "any", a nullable column plus a rebuilt key, built post-RC1. `IRoleProvider` gains `GetAssignmentsForUserAsync` returning assignments with their constraint. **The existing `GetRolesForUserAsync` keeps its signature and is defined to return only unconstrained assignments**, so any caller that is not migrated can never treat a constrained assignment as a wide one (fail closed). The Platform Administrator role and every system role are unconstrained only. The subset rules extend naturally: an actor may assign a role at constraint `K` only if they hold its permissions at a constraint that contains `K` | Scope on each grant inside a role (role explosion: one role per Application, and `PermissionsJson` carries scope in a second place). A parallel `ScopedAssignments` table (two sources of truth) |
| **P-24** | **4. Principal kinds** | `PrincipalKind` is `User` today. The others are added **only when their first consumer ships**, each with its own gate: **ServiceAccount** (persisted, issued credentials; needs a credential and token design, not IAM-10), **Integration** (an identity, P-25), **Agent** (acts on behalf of a user; its authority is the intersection of its own assignments and its delegator's, and never exceeds the delegator). `System` is **not a principal**: it is the absence of one. Scheduler and worker run unevaluated and are never assigned roles (the RC1 acceptance in the audit plan J); audit keeps its own `AuditActor`. `ActorKind.Machine` and `RemoteInstance`, the `ServiceAccount` records, `TrustRelationship` and `GrantedCapability` are annotated dormant in 10.5 (federation withdrawn, D-19). `IRuntimeIdentityService` is **not** dormant (C-4) and is not an actor source | Define all four kinds now (unused types invite premature use) |
| **P-25** | **5. `integration:{id}` semantics** | **An identity, never a containment prefix.** It names the Integration as an acting principal (`PrincipalKind.Integration`) and as the publisher or owner recorded on records, which is the POL-1 need ("an integration always writes its own note set; writing shared data requires an explicit grant"). It is never a `ScopeKey`, never enters the prefix evaluator, and `ScopeKeyConstants` gets no member for it. Operator permissions about integrations (`integration.update` and the SEC-2.1 callback) stay on the existing evaluator, so SEC-2's `P-1` is unchanged. Per-integration operator confinement is not recommended: it has no trigger, and a third axis needs its own gate | A containment scope. Resources that "belong to" an integration are connections (shared by many), schedules, settings and definitions, which is ownership and context, not a scope tree. It would also create a second ownership hierarchy beside ResourceContext |
| **P-26** | **6. One list-filtering contract** | `IAuthorizedContextResolver.ResolveAsync(principal, permission) → ContextAccess`, where `ContextAccess` is `All`, `Only(set of context ids)` or `None`. It is computed from the principal's assignments whose roles grant the permission (axis 1 containment applied to the permission's own scope): any unconstrained match gives `All`; otherwise the union of constrained contexts; none gives `None`. The caller turns it into a **SQL predicate applied before ordering and the row cap**, which is the LST-1.2 binding requirement (no cap-then-authorize). The same call serves lists, search, counts, directory endpoints and dashboards. **Fail closed:** an aggregate that cannot apply a context filter (the audit log's `audit.read`, instance-wide counts) requires `All` and refuses a confined principal. **Shared** appears in a set only when granted explicitly; a confined principal reaches Shared resources through references from the resources it owns, never by listing (details are for the first-consumer gate) | Return the entity list and let callers filter (the Runs defect). A boolean per-endpoint check (cannot express "only these") |
| **P-27** | **RC1 do-not-freeze constraints** | RC1 code must keep these true so nothing above needs a breaking change: (1) `PermissionDefinition` is additive; (2) `EffectivePermissionSet` is the only holder of grant semantics; (3) `GetRolesForUserAsync` means "unconstrained assignments"; (4) role-assignment APIs, DTOs and audit events can gain an optional `contextId` (fields are additive; the lists are arrays of objects); (5) `ScopeKeyConstants` contains no context or integration member; (6) the capability flags are documented as instance-wide, and no UI or API may present them as per-Application; (7) the module authoring guide and the administrator documentation state D-12 honestly: **guests cannot be confined to one Application in RC1; confinement is by capability and by module** | |

## 8. Risks

| # | Risk | Mitigation |
|---|---|---|
| R-1 | A permission flagged for step-up locks out a function on an instance with no mechanism configured | Only the IAM-11 recovery permission is flagged in RC1; `StepUpNotConfigured` is a distinct reason the UI explains; OPS-1 owns making a mechanism part of the supported install |
| R-2 | The viability-aware predicate refuses an operation that used to succeed (C-1) | Stated as intended; refusal codes unchanged; the UI explains the cause (10.4); the owner confirms in OQ-3 |
| R-3 | The preserving step leaves existing `role.manage`-only roles root-equivalent, now explicitly | Visible in the role editor and in the event; the escalation **path** (silent implication) is closed; trimming is an operator decision. Only dev and test databases exist today (SEC-2 closure), so no real installation is affected |
| R-4 | Role-row `UPDLOCK, HOLDLOCK` on assign and edit lengthens a transaction | Role operations are rare operator actions; the role delete already uses the pattern |
| R-5 | Denial rows could be abused to inflate the audit log by an authenticated user | Only enforced denials of Elevated and Critical permissions write; no capability probe writes; a throttle is a separate ruling (the SEC-2 K-4 stance) |
| R-6 | The system-role floor and the repair arrays drift | Test: floor ⊆ repair arrays ⊆ the administrator's grants; the named exception list (G-4) |
| R-7 | A module author understates sensitivity | Declared classification only (ADR-0001: modules are trusted in-process); the platform's own permissions are classified by P-15; documented in the module guide |
| R-8 | The unreferenced scaffolding deleted in 10.1 and 10.3 has an undiscovered reference | `git grep` at each package start; deletion is a compile-time check |
| R-9 | Rebuilding the `UserRoles` key for the assignment constraint (P-23) when the first context consumer ships | Additive until a user may hold the same role at two scopes; designed here so RC1 does not block it (P-27 (3)) |
